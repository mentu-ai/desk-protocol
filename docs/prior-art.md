# Prior art

*2026-09-24. Desk Protocol v0.2.*

This document places the Desk Protocol v0.2 against earlier work: what the desk borrows, what is the same, and what differs. Each primary source was read on 2026-09-24, and quotes were copied from the raw text rather than from summaries. PDFs were converted with `pdftotext`; Nii (1986) was read from page images; the siblings were read from their pinned clones. A research subagent drafted it, every quote was checked by script against the saved source text, and the two findings that change the build's framing (SAMP and grite, section 8) were re-read at source by the builder. Points that could not be checked are marked.

**In short, almost every mechanism in the desk already exists.** The closest precedents are SAMP (one JSONL file per writer in a shared folder, for agents in different tools, with no server), Secure Scuttlebutt (per-author hash chains), Certificate Transparency (gossip of log heads), MCP Agent Mail and grite (advisory leases whose conflicts are reported, not refused) and Kafka (committed positions). The desk's contribution is the combination: a closed grammar of asks, claims, reports, independent verifies and closes, carried in per-writer chained logs that a shell can write.

**A correction to the build prompt.** Its "Why" paragraph says existing options "either need a server ... or stay inside one vendor's product". SAMP (2026-08-08) is a counterexample: it needs no server and works across Claude Code, Codex, Cursor, Copilot, Aider and cron. The desk's documents therefore do not claim to be first at the shared folder of per-writer logs, or at joining with `printf` and `tail` (`docs/decisions.md` row 20).

## 1. Shared coordination spaces

### Linda tuple spaces (Gelernter 1985)

- **What it is.** Processes add tuples to a shared "tuple space" (TS): "until it is explicitly withdrawn, the tuple generated by A has an independent existence in TS." So "Linda allows communication between time-disjoint processes as well".
- **Taken.** Writers and readers need not know each other or run at the same time.
- **Different.** Linda's `in()` is an atomic take: "If two in( ) statements contend for one tuple, one gets it and the other does not". A folder carried by git or file sync has no atomic take. So nothing is removed from a desk, claims are advisory leases, and overlapping claims are flagged `contested`. Each writer has its own log instead of one shared space.
- Source: https://www.cs.unc.edu/~stotts/COMP590-059-f21/slides/lindaGenerative.pdf (copy of ACM TOPLAS 7(1), 1985; the ACM page returned 403), read 2026-09-24.

### Blackboard systems (Hearsay-II 1980; Nii 1986)

- **What it is.** In Hearsay-II, "KSs communicate through a global database called the blackboard", and each hypothesis has "a credibility rating". Nii: interaction happens "solely through the blackboard", and "the knowledge sources are self-activating."
- **Taken.** Specialists that coordinate only through a shared record and decide for themselves when to act, with a credibility on each contribution.
- **Different.** Hearsay-II's "blackboard monitor" queued work for a scheduler; a desk has no scheduler, only each harness's own watcher. A knowledge source could "modify an existing" hypothesis; desk records never change. A blackboard lived in one program; a desk spans harnesses and machines.
- Sources: https://mas.cs.umass.edu/Documents/Erman_Hearsay80.pdf (copy of ACM Computing Surveys 12(2), 1980); https://ojs.aaai.org/aimagazine/index.php/aimagazine/article/view/537; read 2026-09-24.

## 2. Per-author append-only logs

### Secure Scuttlebutt (SSB)

- **What it is.** "Each participant can publish data to their single-writer, append-only log." Each entry has "a backlink in the form of a cryptographic hash of the previous message", and each user "cryptographically signs all their (and only their) messages." The guide: "once a message is posted it cannot be modified."
- **Same.** The desk's per-writer `prev` chain is SSB's feed. SSB allows other carriers ("distribution via a sneakernet could also be used"). SSB messages cite others by hash ID, which pins content, as desk citations do. Replication advertises per feed "the latest message held by the peer for that feed": the desk's `seen` map, minus the digest.
- **Different.** SSB signs everything, and an identity is a key. A desk chain is unsigned by default (SSH signing is optional), so it catches rewrites that others witnessed, not forged history nobody cited. The desk has no network layer. SSB ignores a forked feed and leaves spreading news of forks "open for future work"; the desk reports `rewritten` and gossips heads.
- Sources: https://conferences.sigcomm.org/acm-icn/2019/proceedings/icn19-19.pdf; https://ssbc.github.io/scuttlebutt-protocol-guide/; read 2026-09-24.

### maildir

- **What it is.** "Two words: no locks." Messages are kept one per file ("each message is stored in a separate file with a unique name") and written in `tmp` "before it is moved to new". The format "is reliable even over NFS".
- **Taken.** No two writers share a file, so no locks are needed. Each machine needs its own name (compare the desk's `name@scope`).
- **Different.** Maildir partitions by message and publishes atomically with `rename()`. The desk appends to one file per writer, so readers must ignore an unterminated last line. Maildir mutates: files move to `cur`, the "seen" flag lives in the file name, messages are deleted. The desk is append-only and keeps reader state outside. Maildir has no integrity chain.
- Source: https://cr.yp.to/proto/maildir.html, read 2026-09-24.

### Certificate Transparency and its gossip

- **What it is.** RFC 6962 defines "publicly auditable, append-only, untrusted logs". A log that shows "different things to different people" is caught "by comparing tree roots and consistency proofs", and "All clients should gossip with each other, exchanging STHs at least". RFC 9162 says gossip "is an active area of research and not defined here." draft-ietf-trans-gossip-05 is "Expired (IESG: Dead)". Chuat et al. (2015) offered "the first (to the best of our knowledge) gossip protocols that enable the detection of log inconsistencies."
- **Taken.** `seen` heads in checkpoints are CT gossip at desk scale. Readers who remember digests and report `rewritten` do what CT clients do with tree heads.
- **Different.** CT heads are signed, so two conflicting heads are "cryptographic proof of that log's misbehavior". Unsigned desk heads show that history changed, not who changed it. A desk chain is linear, so checking it means re-reading it; there are no Merkle proofs.
- Sources: https://www.rfc-editor.org/rfc/rfc6962; https://www.rfc-editor.org/rfc/rfc9162; https://datatracker.ietf.org/doc/draft-ietf-trans-gossip/; https://arxiv.org/abs/1511.01514 (abstract only); read 2026-09-24.

## 3. Agent coordination tools

### MCP Agent Mail

- **What it is.** "A mail-like coordination layer for coding agents, exposed as an HTTP-only FastMCP server. It gives agents memorable identities, an inbox/outbox, searchable message history, and voluntary file reservation "leases"". It is "backed by Git (for human-auditable artifacts) and SQLite (for indexing and queries)."
- **Precisely.** *Server:* yes (STDIO also offered). *Git-backed:* yes, but the server writes the repository: it "Writes a canonical message under `messages/YYYY/MM/`, an outbox copy for the sender, and inbox copies for each recipient; commits all artifacts." *Per-writer:* storage is split per agent, but agents do not write it. *Leases:* a reservation "records an advisory lease in DB and writes JSON reservation artifacts in Git; conflicts are reported if overlapping active exclusives exist (reservations are still granted; conflicts are returned alongside grants)." *Acks:* `ack_required`. *Integrity:* signing only for exported bundles; no per-message chain found.
- **Same.** TTL leases whose overlap is reported, not refused: the desk's `contested` rule. Use across Claude Code, Codex and Gemini CLI.
- **Different.** No server or tokens. Each participant writes its own file, with a hash chain, under a grammar with verify and close.
- Source: https://github.com/Dicklesworthstone/mcp_agent_mail (README), read 2026-09-24.

### Beads

- **What it is.** "Distributed graph issue tracker for AI agents, powered by Dolt." Sync uses "`refs/dolt/data` on your git remote; `.beads/issues.jsonl` is an export for viewers and interchange, not the source of truth or a backup." A claim will "Atomically claim a task (sets assignee + in_progress)."
- **Precisely.** *Server:* optional; Dolt runs in-process by default ("single writer"), or as a server for "multiple concurrent writers". *Git-backed:* through a Dolt ref on the git remote. *Per-writer:* no; a shared database with "cell-level merge". *Leases:* none in the README; a claim sets an assignee, and no expiry is mentioned.
- **Same.** Built for coding agents on several machines, with claims and AGENTS.md onboarding. Its hash-based IDs answer the merge problem that the desk answers with one file per writer.
- **Correction.** `paper/file-desk/README.md` says Beads "keeps agents' tasks as JSONL in git". The current README calls that file an export. The repository now redirects to github.com/gastownhall/beads.
- **Different.** A desk is a log of claims and evidence, not a task database. It needs no merge, because no two writers share a file.
- Source: https://github.com/steveyegge/beads (README), read 2026-09-24.

## 4. Agent protocols and conventions

### A2A

- **What it is.** A2A "is an open standard designed to facilitate communication and interoperability between independent, potentially opaque AI agent systems" (release 1.0.0). A receiver "exposes an A2A-compliant endpoint".
- **Taken.** "Opaque Execution": agents share results "without needing to share their internal thoughts, plans, or tool implementations." Desk records carry claims and evidence, not transcripts.
- **Different.** Every receiving agent runs an endpoint; a desk participant runs nothing. On streaming, A2A warns: "Messages MUST NOT be considered a reliable delivery mechanism for critical information." A desk record is durable; only the doorbell can be lost.
- Source: https://a2a-protocol.org/latest/specification/ (read as the raw spec on GitHub), read 2026-09-24.

### MCP resource subscriptions

- **What it is now.** In the current revision (2026-07-28), `subscriptions/listen` "replaces the former `resources/subscribe` RPC and the HTTP GET endpoint." The revision removes "SSE stream resumability and message redelivery", and "the server holds no subscription state across reconnections."
- **Best effort?** The words "best effort" do not appear in the current pages on resources, subscriptions, transports or changes. In effect, a notification sent during a disconnect is lost; the client subscribes again and re-reads.
- **Taken.** A notification is only a doorbell. In a desk the log is the data, so readers re-read from their committed positions.
- Sources: https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions; https://modelcontextprotocol.io/specification/2026-07-28/changelog; https://modelcontextprotocol.io/specification/2026-07-28/server/resources; read 2026-09-24.

### AGENTS.md

- **What it is.** "A simple, open format for guiding coding agents, used by over 60k open-source projects"; "just standard Markdown"; "the closest one takes precedence". It is stewarded by "the Agentic AI Foundation under the Linux Foundation."
- **Taken.** A standard place to teach any harness the desk. Beads and grite already write their instructions there.
- **Different.** AGENTS.md is instructions to obey; desk records are data, never orders. An adapter may put the desk's rules in AGENTS.md, but never record content.
- Source: https://agents.md/, read 2026-09-24.

## 5. Web standards for attributed contributions

### W3C Web Annotation Data Model (Recommendation, 2017)

- **What it is.** An annotation "conveys that the body is related to the target". Its `creator` "may be either a human, an organization or a software agent." Motivations include `assessing`.
- **Same.** A desk `verify` of a `report` is an annotation in shape: a result about another record, by a named creator, with a motivation.
- **Different.** Web Annotation names the intended version with a State (a time or a cached copy), because "Web resources change over time". It has no content digest; "digest", "checksum" and "SHA-256" never occur. A desk citation pins the cited line by digest. There is no log, chain or closure rule.
- Source: https://www.w3.org/TR/annotation-model/, read 2026-09-24.

### ActivityPub (Recommendation, 2018)

- **What it is.** ActivityPub is "a decentralized social networking protocol". Each actor has "An inbox: How they get messages from the world" and "An outbox: How they send messages to others".
- **Same.** A desk log is an outbox: the ordered stream of what one actor published.
- **Different.** No inboxes (readers pull every log), no servers, no POST delivery. An Update means "the object MUST be modified"; the desk appends a superseding record. No integrity chain.
- Source: https://www.w3.org/TR/activitypub/, read 2026-09-24.

## 6. STIX 2.1 and TAXII 2.1 (OASIS Standards, 10 June 2021)

- **STIX.** `created_by_ref` points to "the identity object that describes the entity that created this object." `confidence` "identifies the confidence that the creator has in the correctness of their data" (0–100). An Opinion "is an assessment of the correctness of the information in a STIX Object produced by a different entity." A Sighting "denotes the belief that something in CTI ... was seen." "Only the object creator is permitted to create new versions of a STIX Object."
- **TAXII.** TAXII is "an application layer protocol for the communication of cyber threat information". Clients page with `added_after` and an opaque `next`. Push is reserved: TAXII 2.1 "reserves the keywords required for Channels but does not specify Channel services."
- **Same.** Attributed claims, assessments of others' claims, and the rule that only the creator extends its record. A desk `verify` by a non-reporter is a STIX Opinion in structure.
- **Different.** Both assume servers. STIX `confidence` is self-assigned; desk levels are derived, with ceilings by writer kind. Neither has hash chains or a closure rule. TAXII resumes by timestamp; a desk reader by per-writer sequence.
- Sources: https://docs.oasis-open.org/cti/stix/v2.1/os/stix-v2.1-os.html; https://docs.oasis-open.org/cti/taxii/v2.1/os/taxii-v2.1-os.html; read 2026-09-24.

## 7. The two siblings

### Monitor Protocol

- **What it is.** A server with five parts (monitor, observation, state, subscription, lease). A subscription "reads, does the work, and only then acknowledges"; "A machine cannot claim a person's level of certainty."
- **Taken.** "Kubernetes Lease field names; expiry rule `now > renew_time + lease_duration_seconds`"; at-least-once "(Kafka's wording)"; acknowledging after handling; levels with ceilings; the CloudEvents shape.
- **Different.** A hub with HTTP and tokens, against a folder. The 2026-09-24 audit found that `watch` on `main` still acknowledges on printing. Its gap M3 (no STIX/TAXII, Web Annotation or ActivityPub) applied to the desk too; sections 5 and 6 address it.
- Source: local clone `.siblings/monitor-protocol` (README.md, spec/01-objects.md, spec/04-delivery.md); https://github.com/mentu-ai/monitor-protocol; read 2026-09-24.

### Commitment Protocol

- **What it is.** "An accountability ledger for agent work. ... Evidence is hash-chained, trust-scored, and append-only. State is never stored." Its nine operations include `claim`, `release`, `submit` and `approve`. The Genesis Key "defines who owns the workspace, who can do what, and what requires approval."
- **Taken.** "Closure requires evidence", made strict: an accepted close needs an independent `established` verify. State by replay. Roles shaped like the Genesis Key. The names `machine_verified` and `human_verified`.
- **Different.** "One unbroken hash chain" for all actors, against one chain per writer, so desk writers never contend for a chain head. A Commitment hash "covers its content but not that link", over canonical JSON. A desk `prev` hashes the exact bytes of the previous line, so it covers the link and needs no canonical form.
- Source: local clone `.siblings/commitment-protocol` (README.md, spec/GENESIS.md, spec/TRUST.md); https://github.com/mentu-ai/commitment-protocol; read 2026-09-24.

## 8. Found during the search (not in the brief)

### SAMP / agent-message: the closest precedent for the carrier

- **What it is.** "SAMP is a file-based protocol for asynchronous, durable, sync-safe message exchange between independent processes — typically AI agents". "Two parties agree on a shared directory; they exchange messages by appending JSON lines to per-writer files inside it." "No file has two writers." Folders sync by Syncthing, Dropbox or iCloud; reader watermarks "MUST NOT be synced." It links Claude Code, Codex, Cursor, Copilot, Aider and cron: "If an agent can run `bash`, it can join". Version 1 is dated 2026-08-08.
- **Same.** The desk's carrier: one append-only JSONL file per writer in a shared folder, readers that read all files, local reader state, file sync, and shell-level participation.
- **Different.** SAMP is point-to-point messaging. It has no hash chain (ids are per-message hashes), no claims, leases, verify or close, and "No auth, no encryption." Its inbox advances the watermark right after output (§6, steps 5–6), so acknowledgement follows display, not handling.
- **Consequence.** The folder of per-writer logs is not new. SAMP also contradicts the v0.2 prompt's claim that existing options "either need a server ... or stay inside one vendor's product". system-gap-master (2026) uses the same rule per machine: "each machine writes only its own slot".
- Sources: https://github.com/slima4/agent-message (README.md, SPEC.md); https://github.com/ellmos-ai/system-gap-master; read 2026-09-24.

### grite: the closest precedent for git-carried agent coordination

- **What it is.** "Grite stores issues as an append-only event log inside git refs (`refs/grite/wal`) ... No servers." "Each agent or device gets its own actor ID, local database, and signing key." Content-addressed ids mean "any modification to an event invalidates its ID"; Ed25519 signing is optional. Locks "are optional and designed for coordination, not enforcement", and by default they "warn on conflicts, but continue". Its paper (arXiv:2606.19616) describes an "append-only, signed event log".
- **Same.** For coding agents: no server, carried by git, append-only, content-addressed, optionally signed, with advisory TTL leases that warn rather than block.
- **Different.** One shared log ref, with appends serialized by fast-forward push. Records are CBOR in git objects, so nobody joins with `printf` and `tail`. State is a CRDT projection of issues; there is no ask, verify or close.
- Sources: https://github.com/neul-labs/grite (README.md, docs/git-wal.md, docs/locking.md); https://arxiv.org/abs/2606.19616; read 2026-09-24.

### Claude Code agent teams and cross-session messaging

- **What it is.** "Each agent's mailbox is a JSON file at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`"; "Task claiming uses file locking to prevent race conditions"; one team per session. An incoming cross-session message "can't approve anything", and "Commands don't run".
- **Relation.** A shared-directory medium inside one product. Mailbox files have many writers and claims use file locks, the two things a desk avoids. Its treatment of peer messages matches the desk's principle that records are data, never orders.
- Sources: https://code.claude.com/docs/en/agent-teams; https://code.claude.com/docs/en/cross-session-messaging; read 2026-09-24.

## 9. Short notes (all read 2026-09-24)

- **Kafka.** "The committed offset should be the next message your application will consume"; committing after processing gives "at-least-once" delivery; offsets may live "in a store of its own choosing." Adopted. https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html
- **Kubernetes Lease.** Lease duration "is measured against the time of last observed renewTime." The desk's formula is the Monitor's rendering of that sentence. Across machines, clock skew matters. https://kubernetes.io/docs/reference/kubernetes-api/cluster-resources/lease-v1/
- **CloudEvents 1.0.** "CloudEvents is a vendor-neutral specification for defining the format of event data"; `source` + `id` must be unique. Export only. https://github.com/cloudevents/spec
- **RFC 8785 (JCS).** Canonical JSON so hashing is "reliably repeatable". The desk avoids it by hashing exact bytes. The Commitment form escapes "/" and so is not JCS (§3.2.2.2). https://www.rfc-editor.org/rfc/rfc8785
- **git-bug and Radicle.** git-bug stores "a series of edit `Operation`s" in git with "signed authorship". In Radicle, "The peer is the sole owner and writer of this namespace": the desk's one-directory-per-writer rule. https://github.com/git-bug/git-bug; https://radicle.xyz/guides/protocol
- **Hypercore.** "Hypercore is a secure, distributed append-only log", using "signed merkle trees". https://github.com/holepunchto/hypercore

## Closing table

| Idea | Where it already exists | What the desk adds |
|---|---|---|
| Coordination uncoupled in space and time through a shared medium | Linda; Hearsay-II; Nii | Nothing new; adopted. |
| Self-activating agents on a shared record | Blackboards | Nothing new; adopted, with no scheduler. |
| One append-only, hash-chained log per author | SSB; Hypercore | Nothing new; adopted, unsigned by default, as JSONL. |
| One file per writer in a shared folder; no locks; sync-safe | maildir (per message); SAMP; system-gap-master | Nothing new; adopted. |
| Per-writer partitions in git, so merges never conflict | Radicle | Nothing new; applied to a log folder. |
| Citations pin cited content by hash | SSB; git; grite | Applied to evidence items, so a rewrite of a cited line is caught even if its writer re-forges the chain. Mechanism not new. |
| Gossip of observed heads | CT (RFC 6962; trans-gossip; Chuat et al.); SSB replication | In-band in checkpoints, with digests; weaker than CT (unsigned by default). |
| Advisory TTL leases; overlap reported, not refused | Agent Mail; grite; Kubernetes; Monitor | Nothing new; adopted. |
| Committed next position; ack after handling; at-least-once | Kafka; Monitor | Nothing new; adopted. |
| Reader state outside the shared medium | Kafka; SAMP | Nothing new; adopted. |
| Attributed assessment of another's claim; only the creator extends its own record | STIX (Opinion, Sighting, versioning); Web Annotation; SSB | Nothing new. |
| Credibility levels on claims | Hearsay-II; STIX; Monitor; Commitment | Derived levels with writer-kind ceilings, from the Monitor. New only outside the family. |
| Closure requires evidence | Commitment (`submit`, `approve`) | An accepted close needs an `established` verify by someone other than the reporter, checkable from the records. Small. |
| An ask states what would settle it, with a deadline | Pre-registration ("specifying your research plan in advance", COS); markets resolved "according to the market's pre-defined rules" (Polymarket) | Not found in any agent-coordination system surveyed. Not a claim to be first. |
| Heartbeats give silence a meaning | Kubernetes Lease renewals; Monitor | Adopted; checkpoints add a resume summary and `seen` heads. |
| Records are data, never orders | Claude Code peer messages | A protocol rule across harnesses. The rule is not new. |
| Join with `printf >>` and `tail` | SAMP | Nothing new. |
| Seven operations mixing coordination and evidence in per-writer logs | Pieces in Commitment, Agent Mail, Beads, grite | The combination. Each piece exists. |
| CloudEvents export | CloudEvents 1.0 | Adopted. |
